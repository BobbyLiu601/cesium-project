# ADR 0007：cesium-project 采用 worktree 执行模式

- 状态：已接受
- 日期：2026-11-15
- 延续：ADR 0005 的任务分支交付边界

## 背景

项目原先通过 `local_directory` 的 `in_place` 模式运行任务。所有任务直接使用同一个本地工作目录，daemon 按目录互斥执行，因此同一项目中的不同 Issue 也会排队。项目需要让不同 Issue 并行推进，同时保留每个任务独立的文件修改空间和可审查的 Git 交付结果。

当前 runtime 已声明支持 `local-worktree-v1`，仓库是至少包含一个提交的 Git 仓库，主工作区 `F:\project\cesium-project` 保持为人工使用的主检出。切换只影响后续任务，不迁移正在运行的 `in_place` 任务。

## 决策

- 项目的 `local_directory` 资源使用 `worktree` 执行模式。不同 Issue 可以并发执行；同一 Issue + 同一智能体仍按服务端规则串行，不承诺同一 Issue 的多智能体并行。
- Multica 为每个任务创建独立工作树，并沿用平台任务分支作为同一 Issue 后续轮次的续写依据。平台任务分支不得手工改名、删除或替换。
- 项目继续保留 `<type>/<issue-key>-<slug>` 交付分支约定。每次交付时，交付分支与平台任务分支指向同一提交；首次创建从平台任务分支建立，之后只允许快进。两者不能快进到同一提交时停止并询问。
- 交付时报告平台任务分支、交付分支和相同提交哈希，并推送交付分支。`main` 不自动更新，不自动创建 PR，也不自动合并；ADR 0005 的显式合并授权规则继续适用。
- 新工作树只包含 Git 跟踪内容，不继承 `.env`、`node_modules`、`.cache` 等被忽略文件。任务开始后运行 `pnpm install --frozen-lockfile`；需要真实天地图 token 做人工视觉检查时由执行者临时提供，不自动复制本地密钥。
- 并发任务可能修改相同文件；工作树隔离只避免执行期互相覆盖，不会消除集成阶段的 Git 冲突。冲突在交付或显式合并阶段解决，不能用强制推送或覆盖其他任务结果来规避。

## 备选方案

- 继续使用 `in_place`：不增加工作树和依赖安装成本，但同一项目的不同 Issue 仍受目录互斥限制，不能解决并发排队。
- 只使用平台任务分支：流程最简单，但会放弃现有 `<type>/<issue-key>-<slug>` 交付命名和审查习惯。
- 重命名平台任务分支：表面上保留单一分支名，但会破坏 Multica 对同一 Issue 后续工作树的归属记录，可能导致续写中断或回退到新的回退分支。
- 等待平台支持自定义分支模板：可以同时保留两类命名，但当前没有该配置能力，无法满足本 Issue 的即时并发目标。

## 影响

- 同一项目的不同 Issue 获得并行执行能力，但会同时争用 CPU、内存、磁盘和构建资源。
- 人工主检出不再被任务直接修改；任务结果先出现在独立工作树和分支中，需要显式审查、推送和合并。
- 每个新工作树都要重新安装依赖；真实本地环境变量不会自动传播，首次运行需要执行者确认必要配置。
- 每个 Issue 会有平台任务分支和交付分支两个名字，审查和清理时必须同时识别，不能把一个分支的提交误认为另一个分支的最新结果。
- 同一 Issue 的后续评论仍需等待前一轮结束。需要并行的工作必须拆成不同 Issue，不能依赖同一 Issue 内的多轮并发。
