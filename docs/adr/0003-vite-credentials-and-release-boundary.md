# ADR 0003：VITE 凭据与发布边界

- 状态：已接受
- 日期：2026-11-04

## 背景

三维地球弹窗需要在浏览器中请求天地图 WMTS 服务，因此构建产物必须包含天地图 token。当前项目使用 Vite 的 `VITE_` 环境变量在构建时注入该值，生产构建通过 GitHub Actions 的 `production` Environment Secret 提供 token。

这一方案容易被误认为“服务端秘密”：`VITE_` 变量会被写入浏览器 JavaScript 和网络请求，任何访问站点的人都可以看到。同时，Release Build 只负责上传构建产物，不负责部署。如果这些边界不记录，后续开发可能重新提出运行时配置、后端代理或自动部署方案，或者把密钥扫描通过误认为运营风险已经解决。

## 决策

- 继续使用构建时 `VITE_` 注入天地图 token，不引入运行时配置接口或后端代理。
- 生产构建使用 GitHub Environment `production` 中的 `TIANDITU_TOKEN` Secret，并在构建步骤映射为 `VITE_TIANDITU_TOKEN`。
- 明确 `VITE_` 凭据属于公开客户端凭据，不是服务端秘密。只能使用支持来源域名限制、可轮换的客户端密钥。
- Release Build 只验证、构建并上传 `dist` 产物，不执行部署，也不持有托管平台凭据。
- 密钥轮换和天地图允许域名配置属于维护者的外部前置项。代码中的密钥扫描、构建门禁和 workflow 检查通过，不代表这些运营操作已经完成。
- 不通过长篇 `AGENTS.md` 规则重复本决策；执行方法写入 `docs/CODING_STANDARDS.md`，机械约束由自动化检查执行。

## 影响

- 后续 agent 和审查者应从本 ADR 了解为什么使用 `VITE_` 注入，不应重新提出运行时配置或后端代理方案，除非产品需求发生明确变化。
- 任何进入浏览器产物的凭据都必须按公开信息对待，并通过域名限制、最小权限和定期轮换降低风险。
- 发布流程与部署流程保持分离；部署到具体托管平台需要单独设计和审查。
- 密钥扫描只能阻止新的凭据进入提交内容，不能替代已经暴露密钥的轮换和允许域名配置。
