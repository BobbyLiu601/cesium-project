# ADR 0005：任务交付采用分支提交且不自动合并 main

- 状态：已接受
- 日期：2026-11-07
- 取代：ADR 0004

## 背景

ADR 0004 要求任务完成后自动 rebase、fast-forward 合入 `main` 并推送。这会让执行者默认更新主干，无法保证所有改动都在任务分支上留下提交，也使用户失去合并前的审查时点。新的约定需要把任务执行固定在任务分支上，并让合并成为显式授权动作。

## 决策

- 除只读调查外，每个 Issue 使用一个任务分支，同一 Issue 的多轮执行复用该分支。
- 每次有文件改动的执行必须在交付前提交；覆盖代码、文档和配置，交付时不得遗留应提交的未提交改动。
- 任务完成后默认只推送任务分支，交付分支名和提交哈希；`main` 保持不变，不自动创建 PR，也不自动合并。
- 只有用户在具体 Issue 或评论中明确授权时，才允许 rebase 最新 `origin/main`、运行 `pnpm verify`、fast-forward 合入 `main` 并推送。远端保护拒绝时停止并报告。
- 通过 `simple-git-hooks` 增加 `pre-commit` 和 `pre-push` 守卫，阻止在 `main` 上提交或向远端 `main` 推送。显式授权合并时使用带非空原因的环境变量放行，不使用 `--no-verify`。
- 已推送任务分支只在用户要求同步或明确授权合并时 rebase；更新任务分支最多使用 `--force-with-lease`，禁止强推 `main`。

## 备选方案

- 继续自动 fast-forward 合入 `main`：保留线性历史，但默认更新主干，与用户的交付边界冲突。
- 默认创建 PR：便于远端评审，但超出了“只交付任务分支”的最小要求；用户可按具体任务要求创建 PR。
- 只修改文档、不增加 Git 守卫：实现简单，但无法阻止误在 `main` 上提交或直推。

## 影响

- 任务分支成为每次执行的唯一写入位置，提交和交付边界更清晰。
- 默认交付不会更新 `main`，增加了用户或后续显式合并步骤。
- rebase 不再在每次交付时自动发生，未合并任务分支可能与 `main` 暂时分叉。
- 远端分支保护仍需仓库管理员人工确认；本地守卫只防止误操作，不替代远端保护。
